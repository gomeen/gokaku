# 首阶段技术选型决定

日期：2026-10-30。依据[产品要求](product.md)、[冻结的收敛方案](input-selection-decision-plan.md)、已有[中文核心实验](input-engine-benchmark.md)与[翻译实验](translation-benchmark.md)，以及本轮独立质量集和受控 AppKit 实验。

## 决定

**中文底座选 libime 1.1.17＋已测出厂词典／语言模型，使用内置 Xiaohe。macOS 前端采用自建 InputMethodKit＋AppKit，Swift 管理会话与界面，Objective-C++／C ABI 薄桥接调用 C++ 核心。** 不以青简或整个 Fcitx 作为项目底座，不建设多引擎插件平台，不继续穷举未装配路线。

这是一项有依据的首阶段工程选择，不是声称 libime 在所有语料、硬件或前端中最快。保留轻薄的候选／提交接口是为了隔离输入会话与核心状态，不代表继续维护多个生产后端。

**翻译 runtime 保留 CTranslate2 的独立进程路线，但本轮已测 OPUS 与 M2M100 均拒绝作为默认翻译模型。** 单词、短语表达资源尚没有完成可直接分发的内容验收，也不在此虚构一个已合格语言包。

因此结论分为两项：

- **中文实现路线：可以据此开始工程实现，不再等待更多同类引擎调研。** 本文选择的是路线，尚未把它实现为系统输入源。
- **完整离线双向学习产品：当前不通过。** 缺少合格自由句翻译后端；词典／表达包、真实宿主和翻译并发也没有完整验收。不能把中文底座的选择包装为整个产品已经能按需求交付，不以降级成词级演示冒充整句目标完成。

Gogaku 自身许可证仍由项目另行决定。这里没有替用户选择 GPL 或闭源；libime 的 LGPL 义务仍须履行。

## 为什么选 libime，而不是其他已测组合

| 组合 | 决定与依据 |
| --- | --- |
| **libime 出厂组合 I0** | **采用。** 两个不同中文集合共120条，首选109、前十完整目标112。与雾凇同为109条首选，不能据此说质量更好；雾凇有两条前十优势。libime 在多轮核心实验及本轮节奏测试中中位成本较低，p95有竞争力，直接的小鹤、部分选择与学习API足以支撑自有前端，不依赖生产Lua链。接受约100–104 MiB的轮末RSS采样成本，明确其高于雾凇。 |
| Rime 雾凇 R1 | 不作默认。是最强对照，120条首选109、前十114；本轮核心p99也略低。没有质量或功能失败导致淘汰。取舍是libime中位/p95成本、直接集成与依赖控制，代价是放弃这两条前十收益和雾凇较低RSS；不宣称libime全面支配雾凇，不把GPL义务当成性能缺陷。 |
| 青简统计配置 Q0 | 不采用为底座。中位核心成本低，但独立集首选61/80，技术词仅5/10、工作6/10，且既有长尾和RSS较高；译词接缝不抵消中文质量与数据来源缺口。这里只评价所测统计配置，不外推其未启用神经方案。 |
| 万象标准版小鹤 R2 | 不作默认。独立集首选73/80，优于libime的71，属于真实收益；120条前十114。但已有两轮核心p99为43.58／53.30 ms，明显高于其余竞争配置。对本项目实际输入性能优先的要求，当前所测配置的收益不足以接受该成本。未进行grammar/Lua消融，不宣称其他万象配置一定慢。 |
| 官方Rime小鹤 R0 | 仅保留历史机制基线。核心速度快，但120条前十104，长句覆盖显著不足；不能以它代表现代Rime质量。 |
| libpinyin、SunPinyin、Google开放拼音 | 不继续装配。当前没有本项目证据表明能改变上述取舍，且部分材料的授权或小鹤适配仍不明确。这是停止继续投入的决定，不是判定它们速度差。 |
| 完整Fcitx、OpenVanilla、改造现有前端 | 不作为首阶段底座。它们尚无同机UI性能对照，不凭WebView或语言宣布慢。自建原生路线能直接控制Gogaku特有的候选、英语诊断和会话边界；既然还需这些定制，当前不承担完整框架适配范围。 |

## 新增独立质量证据

80条合成保留样例在看输出前冻结，SHA256 `9fe6a73fdfb18165b3b2fd202365925307d3132a6c8381ada2f24e0d67cb3c2b`。八层各10条：日常、工作、技术、实体、长句、歧义、多音字、零声母。原40条未重复，按键按已有小鹤映射独立复算；本轮所有配置均实际查询并选择匹配项。

| 配置 | 新80条首选 | 新80条前十／完整提交 | 原40＋新80首选 | 原40＋新80前十／完整提交 |
| --- | ---: | ---: | ---: | ---: |
| Q0 | 61 | 70 | 98 | 108 |
| R0 | 66 | 69 | 100 | 104 |
| R1 | 70 | 75 | 109 | 114 |
| R2 | 73 | 75 | 112 | 114 |
| I0 | 71 | 73 | 109 | 112 |

这是冻结目标命中，不是全部合法中文的判定。例如新集 `jing li` 的目标预标「经历／精力」，没穷举「经理」；`ji qi` 预标「机器／及其」，没穷举「极其」。雾凇的这两条首选虽然未匹配目标，不能据此认定为错字。保持原评分不按输出改答案，另保存[标签局限审计](../probes/results/input-selection-holdout/label-audit.json)。一两条差距不作为质量胜负证据。

长句漏整句不等于无法分段输入。I0仍会出现「为服务架构」「容器景象」「会议结束后请把既要……」等问题，选择它不代表中文质量零缺陷。没有针对这些答案临时加词或调参美化成绩。

[独立集汇总](../probes/results/input-selection-holdout/summary.json)和[全部真实候选](../probes/results/input-selection-holdout/quality-outputs.md)保留逐步commit与未完成状态。每套只运行一次质量pass，独立复算汇总通过。

## 固定节奏与原生客户端结果

同一个Swift／AppKit受控客户端，三个核心均通过：带既有文字及emoji的预编辑、完整提交、非首项选择、部分选择后完成、退格后取消。实际读取 `NSTextView.string` 与 marked range，确认没有重复提交或删除既有文字。这是自编适配器加受控文本视图测试，**不是IMK激活、外部聊天应用或真实焦点切换验收**。

固定8条已有回归样例，每轮78键，3轮交错，共702个正式按键，每配置234个。按键预定间隔100 ms，每句单独起始；记录预定、实际派发、worker返回与AppKit返回，计入迟到及积压，不用每个响应后的新间隔掩盖排队。

正式布局更新pass不逐键截图。单位ms：

| 配置 | 核心p50 | 核心p95 | 核心p99 | AppKit布局准备p95 | 预定按键→布局返回p95 | 同路径p99 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Q0 | 2.67 | 13.45 | 21.42 | 2.70 | 20.85 | 229.07 |
| R1 | 7.28 | 12.31 | 14.26 | 2.66 | 19.97 | 26.54 |
| I0 | 4.24 | 10.57 | 16.67 | 2.51 | 17.29 | 27.41 |

完整路径包含两个stdio进程的通信、JSON及排队；生产选型采用薄桥接而非这个测试协议，但未实测该桥接，所以不声称去掉stdio后必然快多少。Q0有一次411 ms worker往返，对应核心计时没有同等长度，不能把全部超时归因于解码算法。所有慢样本保留，不删除离群值。

**这批不是正常频率基准。** CPU速度限制起止33／22，1分钟load average约195／130，每轮也保存热状态。每配置234键只用于验证节奏与成本边界，p99尾部样本少；已有每配置两轮各10,560键的核心记录仍是更大的热态样本。没有为得到正常数字反复重测、关闭节能或终止用户程序。

[布局pass原始汇总](../probes/results/input-selection-layout/summary.json)与各轮事件均保留。此处只能说明**布局更新准备返回**，不是屏幕候选可见时间，更不是宿主已经收字；不能据这张表宣布产品p95/p99验收达标。

### 装置修正，不挑快成绩

最初装置每键同步 `cacheDisplay`，离屏位图耗时p95约135–233 ms，造成数百毫秒甚至秒级积压。这是强制同步截图诊断，不是正常AppKit候选更新路径，不能给引擎或前端排名。该pass完整保存在[原始位图诊断](../probes/results/input-selection-paced/summary.json)，并保存了当时源码快照。修正后将位图移为显式可选诊断，再执行一次布局pass；没有从旧批删除慢记录，也没有将前后差额全部解释为截图消除收益——系统负载也变化了。

## 翻译：明确拒绝，不用速度掩盖质量

- **推理runtime：采用独立进程的CTranslate2工程路线。** 依据已有实际INT8/FP32推理、内存、禁网和OpenMP隔离证据，不采用本机已测较慢且缺算子的Torch MPS回退作为默认。两线程只是已有实验起点，不是未经并发验收的永久最优参数。
- **OPUS：拒绝作为默认。** `tomorrow → 明天见` 增义，`good morning` 重复，错拼输入有空输出或不可靠结果；beam/精度变化没有消除整体问题。
- **M2M100：拒绝作为默认。** 存在上午下午互换、编造名称等改变意思的输出，且更慢；多语言支持不能抵消已见质量失败。
- **Apple Translation：不计为已测合格方案。** 已有结果只有supported、未安装，没有译文。没有为了补一个“冠军”静默下载系统资源或改动用户配置。
- **不以词典替代已确认的自由句目标。** 词典与表达包仍需具体内容与许可验收；没有合格模型时明确整句要求未满足，而不是强选一个已失败模型。

### 本轮没有补完的真实翻译并发

原 `/tmp/gogaku-benchmark/models/` 与HF缓存中的权重、分词器及转换产物已不存在。MiniMax子代理恢复了原固定版本CT2推理venv，但没有恢复权重；完整恢复需要重新下载约624 MB源权重、安装Torch转换依赖并转换。按收敛要求停止为已被质量否决模型重建大材料，没有生成新的译文，也没有使用假CPU负载冒充翻译。

所以本轮正式节奏结果明确标记 `no_translation_materials`，`translation_requests=0`。**真实翻译并发、候选可见延迟、IMK与外部宿主仍未验收。** 这些限制意味着完整学习输入不可判为已通过；不能将重背景负载等同于翻译并发。恢复动作与缺失身份记录见[材料恢复记录](../probes/results/input-selection-native-admission/translation-materials.json)。

## 许可取舍与发布边界

- libime与已测出厂数据有LGPL-2.1-or-later的源码／REUSE声明；数据压缩包自身未附完整许可文本，分发须补齐对应声明、署名及适用文本。动态库替换、对应源码／修改、传递依赖也进入发布清单，不把动态链接当作自动完成合规。
- 雾凇是GPL-3.0-only，不是禁止商业使用，也不能仅据此称它与GPL-3.0-or-later绝对不兼容：后者可选择v3。具体整体发布方式需符合实际组合的条款。本次不以未经选择的闭源要求淘汰它。
- 青简的字表、常用词表转录和general详细来源存在授权核实缺口。将Gogaku改为GPL并不能自动补上第三方数据的权利链。
- 万象主方案仓库与万象数据仓库分别检查；数据仓库的`LICENSE-SCOPE.md`对其原创程序代码保留授权，**不能扩大解释为所有万象主仓库Lua均不可用**。第三方及生成资源保留原许可；不复制未经授权的构建代码。
- 当前鼠须管内的Rime插件有实际二进制哈希，但精确源码提交及构建参数未完整固定。生产分发若采用该路线需重新取得可复现依赖；本轮没有把用户已装bundle复制进产品。

上述不是法律保证。没有已证实禁止使用就不误标禁用；没有核实全部权利链也不宣称已完成发布许可审计。

## 停止本轮选型

本轮到此停止中文引擎扩选与同类基准。后续统一按[首阶段实施总计划](implementation-plan.md)推进；若开展实现，按已选libime＋原生前端交付一个系统输入闭环，不再先造后台管理、多引擎框架或另一套演示来代替输入实现。

选型已经给出；未通过的完整学习产品也明确给出No-go。只有新的合格语言资源、具体宿主失败或可改变上述取舍的实证才构成重开对应决定的理由，不以“还能再研究”作为无限推迟选择的理由。
