# macOS 输入与离线能力验证

目标是在真实 macOS 环境核实 Gogaku 的可行性，首阶段包含小鹤双拼、中英双向学习输入、选词即上屏和用户英语错误提示。本页主要记录首轮源码核查、核心单元测试和隔离 API 探针。后续已完成[真实离线翻译实验](translation-benchmark.md)与[五套小鹤配置的候选／逐键核心实测](input-engine-benchmark.md)。候选持续扩展，libpinyin、SunPinyin、Google 开放拼音及不同前端的接口核查见[其他路线](research-ime-alternatives.md)。尚未安装或启用 Gogaku 输入法，也没有改动用户现有输入法配置。

## 结论

中文输入、小鹤双拼、译词直接提交及英语检查都有可用基础，不需要从零重写整套中文引擎。但不能把青简或 Rime 直接换名字就视为 Gogaku 已完成。

| 需求 | 本轮证据 | 结论边界 |
| --- | --- | --- |
| 小鹤双拼输入中文 | 青简双拼测试通过；后续青简统计配置、librime 官方／雾凇／万象、libime 出厂数据均已实际查询、选择与提交 | 核心可运行及有限样例证据，不等于 Gogaku 系统输入法已接入 |
| 中文选词后直接输出英语 | 青简有 `commit_translation`；相关核心测试通过。Rime 前端可消费引擎 commit 后向宿主插入文本 | 有复用接缝，仍需改学习模式分派、义项选择及部分候选处理 |
| 英→中容错与波浪线 | 系统拼写接口标出 `metting`；原生文本视图能设置并读回拼写标记属性 | 不证明拼错输入一定能翻译，也未验证点击说明的原生界面 |
| 语法提示 | 系统接口对几个合成错误句返回了问题范围，对照正确句未返回问题 | 只证明样例可行，不是语法检查覆盖率或误报验收 |
| 快捷键、菜单、按应用记忆学习模式 | 两个项目都有部分菜单或模式基础，但没有完整 Gogaku 语义 | 需要前端实现，不能把现有中英切换或 `app_options` 当作已完成 |
| 离线自由句翻译 | 后续已实际运行 OPUS/M2M100、五轮热延迟与禁止网络的进程验证；Apple 仍只有 supported 状态 | 两模型都有语义、重复或编造问题，尚无产品级质量验收；详见[实测报告](translation-benchmark.md) |

## 本机与测试范围

本机为 Intel x86_64 MacBookPro16,1，macOS 26.7.2，内存 68,719,476,736 bytes。使用 Swift 6.3.3 和 CommandLineTools，已安装鼠须管 1.1.2，其中 librime 为 1.16.0。

青简安装版本为 `0.3.2-dev-dfdf8408+`；源码核查与核心测试使用另行浅克隆的固定提交，不代表安装版本的运行表现。版本、库校验值和源码提交见 [environment.json](../probes/results/environment.json)。外部源码位于 `/tmp/gogaku-validation/`，未复制进 Gogaku。

## 小鹤双拼实测

探针使用鼠须管自带的 librime 动态库及 1.16.0 对应 API 头文件。官方 `double_pinyin_flypy` schema 在临时用户目录部署，词典和依赖读取安装包自带的公共资源，不读取个人词库。

| 按键 | 实际候选或操作 | 引擎提交结果 |
| --- | --- | --- |
| `nihc` | 首候选「你好」，空格选择 | 你好 |
| `kdhv` | 首候选「开会」，空格选择 | 开会 |
| `hvyi` | 首候选「回忆」，明确选择第二候选「会议」 | 会议 |
| `woxlxtykyu` | 首候选「我想学英语」，空格选择 | 我想学英语 |
| `wxqcf` | 官方原始方案没有候选 | 空格提交原编码，不能据此推广到社区方案 |
| `meeting` | 在双拼方案下出现拼音相关候选，而非英语翻译候选 | 不能用该中文方案直接承接英→中学习输入 |

这些是引擎候选与 commit API 的实际输出，不是向真实聊天应用打字。原始结果见 [rime-flypy.json](../probes/results/rime-flypy.json)。候选排序只代表隔离词库与该次状态，例如 `hvyi` 不能不经选择就固定当作「会议」。

青简在固定提交上实际运行 `qingjian-core` 的 `shuangpin` 名称筛选测试，38 项通过；`translation` 名称筛选测试，21 项通过。这是选定测试，不是全项目测试。前者覆盖小鹤解码、候选与缓冲消耗，后者包含词级译词提交与翻译接口的模拟边界，不是模型翻译质量测试。

日志见 [双拼测试](../probes/results/qingjian-shuangpin-tests.txt)与[翻译相关测试](../probes/results/qingjian-translation-tests.txt)。编译与测试耗时不作为输入法速度指标。

## 英语检查实测

使用 `NSSpellChecker`，每次指定 `en_US`，不修改用户词典，不调用自动纠正或替换接口。

- `meeting`、`tomorrow` 没有拼写标记，`metting` 与 `meeetingg` 被标记。
- `I have a metting tomorrow.` 中只标记了疑似问题词。
- `He go to work.`、`She have a meeting.` 和 `I has an apple.` 返回语法问题范围；对照 `He goes to work.` 没有返回语法问题。
- `Gogaku` 被当作疑似拼写问题，说明品牌和自定义词免标策略有实际必要。
- 本次网址与邮箱样例没有标记，不代表所有网址、邮箱或代码都能自动免标。
- 独立 `NSTextView` 中的拼写临时属性设置后读回成功，未进行屏幕绘制、鼠标交互或宿主正文标记测试。

普通执行与使用 `sandbox-exec` 禁止探针进程网络访问时的结果相同。系统拼写服务通过进程外机制工作，本轮没有断开全机网络，因此不能据进程沙箱结果承诺所有系统服务都已完成断网验收。

结果见 [macos-text-check.json](../probes/results/macos-text-check.json)与[受限进程结果](../probes/results/macos-text-check-restricted.json)。SDK 中 `NSSpellChecker.h` 的检查接口及 `NSTextView.h` 的 `setSpellingState:range:` 是本次原生调用依据。

## 两个底座的关键差异

### 青简更接近现有学习需求，但不是现成学习模式

源码已有小鹤、英文候选、双向词级释义和 `commit_translation`，可作为优先评估的复用路径。普通候选仍走中文提交，不能只改一个调用就保证所有部分选词稳定输出英语。

`commit_translation` 会带上此前暂存内容，需要防止夹带中文。双拼下的拼音头与英语尾混输明确禁用，但独立英文模式仍存在。不要把两者混为同一个缺口。

macOS 当前模式和菜单不等于按应用保存学习方向；停用输入法时原文提交行为也与 Gogaku 的草稿保留要求不同。用户英语波浪线、点击说明、模式记忆和焦点安全需要新增前端逻辑。

来源与固定提交引用见[青简源码核查](research-qingjian.md)。

### Rime 适合作为中文引擎基线，不能只靠配置解决整个产品

Rime 官方小鹤方案与候选提交已在本机验证。当前鼠须管安装包包含 Lua 插件，但插件存在不等于某个 schema 已启用它。

引擎的 translator 与 filter 候选链是同步消费的，不建议直接在其中等待慢模型。词典或缓存命中可以走轻量路径，模型任务需要独立执行并校验输入版本。只改候选 comment 也不会把译文提交，必须明确最终候选文本。

英→中不能直接开启 ASCII 直通，否则字母绕过翻译候选；也不能简单放在小鹤拼音路径里。标准引擎上下文不提供通用富文本错误区间和点击事件，波浪线与说明需要自有前端。

来源与固定提交引用见 [Rime 支撑边界](research-rime.md)。

## 翻译模型的后续实测

首次探针时已核对两个方向的 OPUS-MT model card 与 CTranslate2 对 macOS x86-64 的支持。两个单向模型的许可不同，英→中标注 Apache-2.0，中→英标注 CC-BY-4.0，不能当作同一个许可包。来源筛选见[离线组件筛选](research-offline-components.md)。后续在隔离目录下载并转换 OPUS 两方向与 M2M100，完成真实推理、五轮延迟、内存和禁网进程验证，结果见[翻译实测](translation-benchmark.md)。

本机另行编译运行了 Apple Translation 探针，使用 macOS 26.4 起的 lowLatency 策略，英→中和中→英均返回 `supported`，没有返回 `installed`。探针仅在已安装时执行翻译，因此未下载语言模型、未发起下载授权、没有取得译文。它不是 Intel 不支持的证据，也不是离线翻译成功的证据。原始结果见 [apple-translation.json](../probes/results/apple-translation.json)。

首次探针未下载权重或安装 runtime，后续实测已补上这一证据缺口。仍不能从模型体积、公开分数或 M 系列数据推断本机速度，也不能承诺 `metting` 会得到「会议」；后续实测确实发现不同精度和搜索策略对此例输出不同。

## 后续最小验证

输入底座保持开放选型。青简、librime 与 libime 已完成首轮核心对照；libpinyin、SunPinyin 等新增引擎及 Fcitx／OpenVanilla 等前端继续按相同门槛验证，不将某个译词接缝或源码结构作为性能冠军证据。

1. 保留已有本地翻译实验基线，继续评估其他模型、词典与短语资源，重点检查本轮出现的质量缺陷。真实推理已在禁止网络的进程中验证，全机断网与重复冷启动分布尚未验收。
2. 构建不替换现有输入法的原生最小样例，先用固定词典验证「小鹤按键 → 中文候选 → 英语候选 → 一次上屏」。同时检查局部选词与剩余编码，不能夹带此前暂存中文。
3. 英→中使用独立英语输入状态，接入系统拼写检查，在自有输入区域显示波浪线和说明。检查失败不自动改词、不阻塞原文提交。
4. 验证按应用记忆、焦点切换、候选版本绑定和真实宿主兼容性。安装、注册或切换输入源前另行说明，不在本轮变更系统。

最终采用青简、librime、libime 或何种前端，仍需质量、性能、宿主兼容性、维护成本与许可的比较。librime 为 BSD-3-Clause，不代表鼠须管或官方小鹤 schema 同为 BSD。青简代码、词典、UI 和模型也必须逐件核对，详见两份源码报告。Gogaku 许可证尚未确定。
