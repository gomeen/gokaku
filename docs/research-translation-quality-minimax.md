# 翻译质量研究：原组合策略的真实瓶颈（独立研究）

> 本文保留子代理的原始独立意见，包含尚未证实或经复核不成立的统计、推断与建议。请结合[汇总与复核](research-translation-quality-synthesis.md)阅读，不将本页直接当作产品决定或验收证据。

- 日期：2026-11-04　性质：**独立复核与建议**，不改变「学习模式保持关闭」的现状，不接生产
- 复核对象：「审核表达／模板优先 + small100 候选生成 + quickmt 反向评分 + 结构检查」
- 证据基线：`probes/results/translation-strategy-final/`（report、acceptance、final-labels、run、requests.jsonl）、`probes/results/translation-backends-round2/final-selection.md`、`probes/translation_strategy.py`、`probes/translation-backend-worker.py`、`native/GogakuCore/translate/translate_safety.cpp`、`resources/translation/`

## 一、结论摘要

**主因不是编排层缺陷，而是候选生成阶段的召回不足。** 我用 1,280 条请求级记录逐条重算后得到一个决定性事实：**模型路径上 91 条错误放行中，没有一条的正确译文出现在候选列表里**（final-labels 标为 fail 的 90 条模型用例，reference 字符串 100% 不在 candidates 中；另 1 条走资源路径）。两个 beam 候选互为近义错译（`stapler`→「斯塔格勒」／「斯塔格尔」，`catch you later`→「接下来捕捉你」／「接下来抓住你」）。

推论：排序层（正向分数、反向评分、λ 加权）在现有候选集上的**理论增益上限是 0**——正确候选不在集内，任何排序都选不出来。这比 `docs/translation-strategy-decision.md` §一「候选生成需要一次解码」的结论更强。

## 二、瓶颈定位

**1) 模型能力（主因）。** small100 是句子级 MT 模型，对中文双字词做**形态直译而非词条翻译**：`外卖`→「External sales」、`报销`→「Replacement」、`保修`→「Guaranteed」、`不用客气`→「No need for guests」、`别客气`→「No guest」。这是退化解码而非「翻译质量差」，词典可直接覆盖。

**2) 解码实现（被忽略的关键变量）。** 官方模型卡与维护者说明默认 **beam size 5、max target length 256**（https://huggingface.co/alirezamsh/small100/discussions/1 ：“We use beam size of 5 and maximum target length of 256”）。但 `run.json` 记 `beamShort=2, beamLong=5`，`probes/translation_strategy.py:496` 固定 `{'short-expression': (2,2), 'short-sentence': (5,3)}`，`probes/translation-backend-worker.py:130,140` 又把 `num_hypotheses` 上限压到 `beam_size`。结果：**200 条应译中 159 条落短表达桶、144 条实际只用了 beam=2 的搜索宽度**，召回被解码宽度直接卡死；反过来预算 2s 的短句桶 p95 仅 527.7ms（4 倍余量）。**beam 分配与延迟预算正好倒置**，且文档从未记录「短表达用 beam=2」的依据。

**3) 加固层实现（有根据的缺陷）。**
- `translate_safety.cpp:818` 脚本校验用**全串汉字数 vs 拉丁字符数**判语向，不排除品牌／版本号：`Open the PR on GitHub.`→「在GitHub上打开 PR。」（汉字 5／拉丁 8）被 `script=1` 误拒；`Update to macOS 15.2.`（4/5）、`Log in with WeChat.`（5/6）同理。
- `translate_safety.cpp:848` 长度比率**按源文语种主导选区间**而非按方向：zh→en 源文含拉丁品牌／版本号时被判非中文源、套用 en→zh 的 1.2 倍上限，`Gogaku 更新到 v1.4.2 了。`→「Gogaku is updated to v1.4.2.」误判 `length=2`。
- `probes/translation_strategy.py:465` 未知词判定只对**整串是单个 ASCII 词**生效，句内错拼从不被识别：`I have a metting tomorrow.` 期望 preserve，实际放行「我明天有一个聚会。」——这是运行时能力缺口，不是单条样例问题。

**4) 验收口径（口径本身在制造噪声）。**
- 报告称「5 条正确译文被误拒」，实为 4 条：`fin-e-063` 参考是「Gogaku v1.4.2 发布了。」，被拒候选是「Gogaku v1.4.2 已退出。」，**它本身是错的**。修好脚本校验的净效果是 **+3 合格、+1 错误放行**，不是 +5。
- `probes/translation_strategy.py:41-48` 桶定义用「汉字数＋英文词数 ≤8」划分，**28 条英文整句**（≥5 词）被算进「短表达／500ms」桶，延迟 p95 是对错误预算口径测出来的。
- 语义标注把「意义破坏／义项偏差／不自然」压成同一个 fail。按报告自身分类，91 条错误放行中意义破坏 65 条、遗漏或不自然 26 条；放松风格判定最多抬几个点，**不接近 95%**。`forecast`→「预计」、`on sale`→「出售」属风格／义项层，不宜与「stapler」→「斯塔格勒」同权。

**高价值漏查（报告未指出）：** ① beam 宽度与召回；② 词级「形态直译」失败族（词典可治）；③ 加固层比率统计须按**方向**而非源文语种取区间；④ 错拼检测只覆盖单词输入；⑤ 验收集用于归因后即失去验收资格，须换新冻结集。

## 三、三个新思路（按价值排序）

**思路一：先修召回——短表达桶恢复 beam=5／num_hypotheses=5（最高优先）**
机制：只改这一个变量，其余（模型、λ=0.25/0、资源、模板、加固层、驱动）按 `probes/results/translation-strategy-freeze.json` 冻结不动。理由：召回是唯一能在不改模型、不改判据前提下直接抬覆盖的旋钮；官方配置本就是 beam=5，本轮降到 2 属**无记录的策略收窄**。针对失败类型：直接命中「正确候选不在 beam 内」这一主因。限制：延迟会涨（CT2 beam 成本随宽度上升、encoder 固定），500ms 需实测；beam=5 不保证覆盖到 95%；实测后该验收集即被用于调参，后续验收须换新冻结集。

**思路二：把词典从「精确命中表」升级为「候选投影／解码约束」（针对词级形态直译）**
机制：`run.json` 已记录本机 CC-CEDICT dump 125,356 条（CC BY-SA 4.0，派生声明见 `resources/translation/manifest.json`），现仅做完整输入精确命中（覆盖 15/200）。改为：对词／短语级输入先用模型生成候选，再把候选**投影**回词典条目——若源词头义项唯一（或可由上下文消歧）而模型输出不是该义项的词典渲染（`报销`→「Replacement」而非 reimburse），则以词典义项替换或直接拒译；也可反向把词典条目作为解码约束候选集（CT2 是否支持需查证）。针对失败类型：覆盖「模型在拆字而非查词」的失败族，是唯一能治「中文双字词」这一 OOD 场景的手段。限制：义项消歧策略要重设（现策略「多义整条不进」正是覆盖上不去的原因）；CC BY-SA 4.0 相同方式共享义务在项目许可未定时是真实分发风险；词典替换也会引入「词条对、语境错」的新错。

**思路三：把验收口径拆成「合格覆盖」与「安全放行」两把尺，并补齐运行时失败检测**
机制：固定风险集与探针继续用「意义破坏」口径（对应产品硬要求「错误猜测不能当可靠候选」），200 条应译集拆成「完全合格／可接受（义项偏差、不自然）／意义破坏」三档分别记分；同时把 `PreserveDetector` 未知词判定扩展到**句内词级**（复用 `resources/english-words.txt` + 编辑距离），把加固层比率统计改为按方向取区间并排除品牌／版本号。针对失败类型：把「必须拒译的错误」与「可以更自然的瑕疵」分开，既不放松安全线、也不因风格问题误判路线死活。限制：改口径不创造质量，属止损而非增益。

**明确判断：「反向评分 + 结构检查 + 审核资源扩容」这一支不值得继续作为主线。** 反向评分在 en→zh 只改变 22/88 条模型用例的取舍，明确救回 `fin-e-096`（「降落」优于「起飞」）与 `fin-e-051`（命中参考「十分钟前」），也明确弄坏 `fin-e-049`（「在早餐」不如「早餐」）；净增益个位数百分点，且**对 91 条错误放行一条都修不了**。结构检查 91 条全过；资源＋模板只覆盖 15/200。继续在这三处加码，是在修一条已证明到不了 95% 的管线。

## 四、事实 / 假设 / 猜想分层

**已证事实（本机记录可复算）**：① 91 条错误放行全部通过结构检查，模型路径 90 条 fail 的参考译文均不在候选集中；② 200 条应译中 144 条 beam=2、41 条 beam=5、15 条非模型路径，官方默认 beam=5；③ 短表达 p95 353.8ms/500ms，短句 p95 527.7ms/2000ms；④ 脚本校验误拒 3 条中文用例（han/latin = 5/8、4/5、5/6），长度误拒 1 条 zh→en，`fin-e-063` 被拒候选本身错误；⑤ 28 条英文整句被归入 500ms 短表达桶，`I have a metting tomorrow.` 在 expectedAction=preserve 下仍被放行；⑥ 词级失败集中在形态直译；⑦ 五轮 1,280 条请求判定完全一致。

**有根据的假设**：提高 beam 宽度能显著抬升「参考译文在候选中」的比例（依据：官方配置 beam=5，错误同族案例的正确候选与 top-1 很近但不在 beam 内）；词典投影能消除大部分词级形态直译失败（失败输出与词典义项字面重合度低，释义可枚举）；句内错拼检测能把一类真实输入从「翻译错」变成「保留原文」，提高安全性但不提高覆盖（依据：探测词表已存在，现实现只匹配单 token）。

**未验证猜想（不得当作结论）**：beam=5 后短表达 p95 仍 ≤500ms（**无任何测量**）；beam=5 后错误放行会下降（候选变多可能使排序变难、错误放行持平甚至上升）；词典投影在开放输入下能保持精确率；CT2 是否支持对 small100 施加词表级解码约束。

## 五、只做一次的最小验证与停止条件

**实验（唯一一次）**：在**同一份** `validation/translation-final-set.json` 上，仅把短表达桶改为 beam=5／num_hypotheses=5，其余按封板文件冻结不动，跑 5 轮交错，同时采集四个量：(a) 参考译文出现在候选中的比例（recall@5）；(b) 合格覆盖（按三档口径重判）；(c) 错误放行数；(d) 短表达 p95。**使用限制**：本次只作测量，其结果不得再用于同一验收集的调参；后续任何验收声明必须换新冻结集。

**停止条件（满足任一即停止 small100 路线，不再做参数扫描）**：① 短表达 p95 > 500ms → 停止（召回换不来延迟合规）；② recall@5 相对 recall@2 提升 < 10 个百分点 → 停止（瓶颈不在 beam）；③ recall@5 ≥ 85% 但合格覆盖仍 < 70% → 停止（证明排序层是瓶颈且现有信号不足），转思路二；④ 合格覆盖 ≥ 80% 且错误放行 ≤ 10 条且 p95 ≤ 500ms → 才允许进入下一轮（词典投影＋句内错拼＋口径修正），不得自动连续。

## 六、现实约束

- **500ms / Intel CPU**：现有 small100 CT2 INT8 产物与 2 线程配置已在 i9-9880H 跑通，双端同产物同参数可行；但「更宽 beam」「更大模型」「用 LLM」是否仍合规**一律无测量，不能声称达标**。仓库既有裁决（死守 500ms、不分层）继续有效，本报告不提议松动。
- **离线**：任何新依赖必须能完全离线装载；CTranslate2／sentencepiece 路径已证明可离线（`HF_HUB_OFFLINE=1`）；云模型与系统翻译 API 不作为本项目默认合规替代。
- **跨平台**：macOS（CT2 dylib）与 Windows（MSVC）必须用同一权重、同一分词、同一语言标记；仓库已记录「同一权重在不同 CPU 后端不保证逐字一致」，故任何变更需两端分别跑同一验收集；Windows 桌面环境未提供前不得声称双端通过。
- **许可**：small100 为 MIT、quickmt 为 CC-BY-4.0、CC-CEDICT 为 **CC BY-SA 4.0**（衍生数据需声明修改，SA 义务在项目许可未定时是真实分发风险）；新模型／新数据必须先逐文件核许可；词典投影会放大 CC-CEDICT 的分发义务，这是思路二的前置问题。
- **不降低产品要求**：不建议放松 95% 门槛或提前开放学习模式；建议把「合格覆盖」与「安全放行」分开度量，并把投入从已证明无效的排序层转到召回与词级词典。

## 七、证据局限

1. 未运行推理、未下载模型、未改生产代码与既有数据；结论全部来自既有 1,280 条请求记录与源码静态审查。
2. 语义判定沿用 `final-labels.json`（agent 逐条审阅，非用户盲测）。已发现至少一处标注／报告口径错误（`fin-e-063`），说明该标注集本身带误差，46.0%／53.0% 有未量化的测量误差。
3. 两轮评测的分母与集合不同（本轮 200 应译＋32 风险；上轮 385 判审），**70.8% 与 49% 不可直接相减比较**，本报告未用该对比做因果推断。
4. 我复核了 91 条错误放行的候选全文后判定「正确候选不在候选集」；对「参考译文是否等同于唯一正确答案（存在同义正确译法）」保持保守估计——即使少数同义正确候选被算作不在集内，结论方向不变，因为正确译法（如「订书机」「reimburse」）与 top-1 的差距远超 beam 内的近义变体。
5. 联网仅成功取得 small100 官方 beam 配置；huggingface.co 正文直连被本地网络策略拦截，未逐字核读模型卡全文与 LICENSE 正文，许可结论沿用仓库既有登记（`docs/validation/native-development.md:101`）。
