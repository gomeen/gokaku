# 输入法整体选型：输入性能与质量优先

调研日期：2026-10-30。依据[产品方向](product.md)、已有[组件验证](feasibility.md)和[翻译实测](translation-benchmark.md)。本文主体是公开文档、固定版本源码及本机 SDK 的设计核查。后续中文逐键核心与候选质量已实际运行，见[首轮实测](input-engine-benchmark.md)；其他解码器和前端见[新增路线](research-ime-alternatives.md)。真实宿主和翻译并发仍未验收。

## 后续选型决定

本文保留前期设计核查背景。后续已完成独立80条中文质量集及受控AppKit测试，选择 **libime出厂组合＋原生InputMethodKit／AppKit**，不再继续扩选中文底座；CTranslate2保留为独立推理路线，但已测OPUS/M2M100拒绝作为默认模型，完整学习产品仍不通过。证据、取舍和未验收边界以[技术选型决定](input-selection-decision.md)为准。下文“下一轮建议”是形成该决定前的研究记录，不作为继续扩张测试的要求。

## 本轮结论

用户明确：实际输入性能第一，技术栈与框架保持开放，后台管理系统没有过高要求。满足小鹤、候选质量和提交正确性后，以连续输入、长尾延迟、资源与翻译并发表现实测选型，再看集成与维护成本。现有青简、Rime、libime 只是首轮对照，不是范围上限。设置、片段列表和资源管理采用足够简单的实现；不能为了后台的技术栈便利牺牲输入体验。

目前仍不能宣布某个输入引擎或翻译模型最好。已有 OPUS CT2 INT8 的 125 ms 是特定混合输入集的热推理轮次中位数，不是每次按键延迟、p95、模型冷启动或宿主上屏时间；其质量也未通过默认上屏要求。

建议先验证以下组合，均为工程建议，未确认为最终技术决定：

- macOS 接入以公开的 InputMethodKit 宿主协议为验证对象；它不是中文解码器，也不限定核心语言或前端框架。原生自建前端、AppKit/其他UI方案及可复用框架均按事件处理、绘制、桥接与提交成本实测，不因使用 Swift、Rust、C++ 或某 UI 框架就认定更快。
- 中文层首轮比较 librime、libime、青简核心，同时补查 libpinyin、SunPinyin 与 Google 开放拼音；满足相同小鹤与质量门槛后继续加入实测。前两者重点评估生产词库与个性化质量，青简保留现有功能接缝的复用价值。Fcitx macOS 是集成路线，与独立前端加 libime 共享解码家族。
- 学习层分词典义项、表达资源、句子模型处理；模型任务与按键处理隔离，普通中文输入不依赖翻译服务成功。
- 后台优先考虑本地设置与简单片段存储，不为首阶段引入管理服务器、分布式服务或重型分析系统。实现形式待定，数据正确性、删除与隐私仍须满足产品要求。

专项证据见[macOS 接入与发布](research-ime-macos.md)、[中文引擎与数据质量](research-ime-engines.md)、[学习输入与资源](research-ime-learning.md)。下文是跨专项的设计判断与验证方案。

本轮新增的优先风险是：IMK 默认取消可能把原文提交，焦点回调不能简单等同于当前输入框身份；词典释义不一定能直接作为发送内容，资源仓库许可也不自动覆盖其第三方数据；异步模型接口在队列满时仍可能阻塞。这些都比后台管理吞吐更直接影响输入体验，必须进入原生验证。

## 要比较的是四种等待

| 用户感受到的过程 | 计时边界 | 主要影响因素 |
| --- | --- | --- |
| 每次打字是否跟手 | 事件到达输入法→预编辑与候选实际显示 | 事件积压、解码、候选枚举、UI、合成显示 |
| 是否容易选到目标 | 第一键→选中目标表达 | 首选质量、翻页、局部选词、候选跳动、误选返工 |
| 学习结果是否来得及 | 有意义的输入版本形成→对应译文候选可见 | 词典覆盖、调度、排队、冷加载、模型、缓存 |
| 选好后是否及时上屏 | 确认操作→正确宿主显示最终文字 | 当前候选身份、提交协议、宿主响应、焦点变化 |

API 返回、UI 提交更新、屏幕真正显示是不同端点。探针和 signpost 可覆盖前两者；“按键到可见”和宿主收字要结合可控宿主、时间线与录屏/显示采样，披露帧率和测量误差，不能用调用 `insertText` 的时间冒充宿主已经显示。

Apple 的响应性指南把约 100 ms 视为离散交互开始可感知的粗阈值，并建议屏幕更新所需的主线程工作尽量在约 5 ms 内完成；它明确强调这些只是粗指导，不是输入法验收标准。[P1] 输入法连续打字应采用更严格、独立的预算。

## 输入链路的建议边界

```mermaid
flowchart LR
    K[键盘事件] --> S[输入会话与模式]
    S --> C[中文解码或独立英语缓冲]
    C --> U[预编辑与候选窗]
    C -. 输入版本快照 .-> L[词典与表达检索 / 模型工作进程]
    L -. 校验版本与会话 .-> U
    U --> G[确认候选并校验当前宿主]
    G --> H[一次提交最终文字]
    G -. 异步记录事件 .-> D[学习片段存储]
    M[设置与资源管理] -. 配置快照 / 完整资源版本 .-> S
```

这是待验证的逻辑边界，不要求一框对应一个进程或微服务。小型确定性解码可以在输入进程内，或使用已验证的轻量 IPC；主线程上只保留足够短的事件处理与 UI 工作。若解码也需移出线程，仍须保持事件顺序和会话所有权，不能让较早按键结果覆盖较新状态。

模型建议放独立工作进程，依据是已有 OpenMP 冲突与崩溃证据，以及隔离加载、故障、内存回收的需要。Apple XPC 是可研究的机制之一；官方文档说明服务可因故障或生命周期管理终止，连接中断必须被处理。[P3] 具体启动、签名、沙箱与驻留行为要在 IMK 宿主下验证，不能把 XPC 等同于永久驻留或自动完成当前请求。

[macOS 专项](research-ime-macos.md)与本机 `IMKInputController.h` 核查出一个直接冲突：默认 `cancelComposition()` 会用原始文字替换 marked text 并调用宿主插入；默认仅接收 keyDown 时，点击组合区外还会触发 `commitComposition:`。所以“取消异步翻译”与“取消宿主组合输入”必须分开，不能直接调用名字像取消的 API 就声称没有上屏。切应用、清空预编辑、原选区恢复和保留草稿要一起验证；公开协议不保证所有宿主的未提交文本能永久保留。

记录和设置只向输入链路提供内存中的小快照；逐键不得等待日志写盘、数据库锁、模型下载、词库部署或设置窗口响应。SQLite 是可选的简单持久化方案，并非已选定；WAL 允许读写并行但仍只有一个 writer，checkpoint 也有成本，不能靠打开 WAL 就保证无阻塞。[P6] 记录队列也要有容量上限；存储故障时继续输入，并明确记录暂停或未保存状态，避免无界积压和虚报保存成功。

## 开发各方面的覆盖清单

以下“要求”沿用已确认产品目标；“建议”和“待测”不改变需求状态。

| 方面 | 对输入体验的影响与本轮处理建议 | 必须留下的验证证据 |
| --- | --- | --- |
| 小鹤解析与编辑 | 连续组词、尾部单键、零声母、分隔符、局部选词、退格重算；英语方向独立，不自动按拼音解释 | 原始按键轨迹、消费区间、候选和提交序列 |
| 中文词库与排序 | 生产词库、频率、语言模型、用户词共同决定命中；包大小和模型参数不代替质量 | 首选/Top-k、额外按键数、姓名新词、歧义长句 |
| 个性化学习 | 普通中文的选词学习与外语学习片段是两回事；记录“采用帮助”不代表掌握；译文不能污染中文词库 | 无学习基线、固定学习轨迹、重启持久化、删除/重置 |
| 双向表达质量 | 英→中与中→英分别验收；词义、词性、语域、否定、数字、时间、人名不能只看通顺 | 双语人工逐条审阅，多义词与上下文样例 |
| 拼写与语法 | 只检查用户英语；完整词后检查；品牌、代码、URL 等需免标；系统接口的离线保证另验 | 正确输入误报率、已知错误召回、标记区间、误报排除 |
| 候选与按键交互 | 空格、Enter、数字键、标点、Esc、方向键和快捷键不能因异步候选到来改变原意 | 结果到达与按键交错的重放；显示项与实际提交一致 |
| 候选窗与说明 | 文字清楚、零基础能理解；鼠标点波浪线不抢错宿主；支持键盘和 VoiceOver 路径 | 缩放、多屏边缘、长文本、暗色、无障碍实测 |
| 宿主文本协议 | marked text、选区、replacement range、UTF-16 与字素边界；撤销和剪贴板由宿主行为共同决定 | AppKit、浏览器、Electron、终端等真实宿主矩阵 |
| 会话与焦点 | 按应用模式不等于按进程永久持有 client；同应用不同窗口/输入框也要隔离 | 切应用/输入框、切模式、鼠标改选区、失焦回调竞态 |
| 资源与并发 | 词典常驻优先；模型按预算预热/释放；线程不能抢满整机；排队需有上限 | 真实打字加模型并发的 p95/p99、CPU、驻留/峰值内存 |
| 耗电与长期运行 | 空闲不能持续轮询或忙等；模型卸载与重载兼顾首次响应；不要关闭系统节能机制保成绩 | 空闲唤醒、CPU 时间、插电/电池、持续负载后的退化 |
| 生命周期与恢复 | 首次激活、重启、睡眠唤醒、锁屏、服务崩溃、资源缺失、磁盘满分别处理 | 能继续普通输入；保留/取消学习输入的可见结果 |
| 隐私与记录 | 只记录 Gogaku 的学习片段；不扩展为全局键盘记录；输入日志、缓存和崩溃附件也可能含隐私；secure input 状态不能可靠定位当前密码框 | 安全字段与不确定路径的退路、暂停、应用排除、删除；性能日志不含原文；禁网验证 |
| 安装与更新 | 输入源注册、签名、公证、架构、模型下载和数据迁移都影响可用性 | 隔离安装/卸载、更新失败恢复、合法且完整的旧资源仍可用 |
| 许可与供应链 | 解码器、前端、插件、词库、统计模型、翻译权重分别审查；固定哈希与来源 | 每份实际分发物的许可、署名、修改说明与来源清单 |
| 多语言与维护 | 语对声明、分词、大小写、空格、双向文字、字体不能全部写死为中文/英语 | 首阶段中英完整闭环；以后逐语对验收，不预先承诺全语言 |

## 中文底座怎样比较

既有[候选路线](input-engine-candidates.md)说明了四条集成方式。此次补充的重点是把“解码器”“词库与语言模型”“前端集成”分别计量。单字双拼映射正确并不代表连续组词好用；词库规模也不代表频率、读音、去重、简繁和新词覆盖合适。

| 候选 | 进入比较的理由 | 首要风险与退出条件 |
| --- | --- | --- |
| librime 加原生前端 | 本机官方小鹤探针已有可复现结果；补入雾凇小鹤、万象标准版小鹤及配套统计 grammar，比较现代生产组合 | 官方最简词库只作机制基线；octagram 是统计语言模型，不是神经大模型。具体配置、插件和数据需独立验证，候选链不应等待慢翻译 |
| libime 加原生前端 | 内置小鹤、上下文解码与学习 API，值得验证候选质量和可控参数 | 本机核心已构建并进入首轮实测；宿主尚未验收，数据依赖、桥接、包体与学习写盘仍须纳入真实成本 |
| Fcitx macOS 加 libime | 可以衡量复用现有前端/插件的收益，并与直接集成共享引擎对照 | 须固定相同引擎与数据才能讨论框架开销；学习输入适配和候选 UI 仍有工作量 |
| 青简核心及现有前端 | 已有小鹤和译词接缝，适合比较复用收益 | 核心测试不代表质量或性能领先；数据许可、中文暂存、局部选词及焦点路径均有待处理 |

不建议首阶段自研拼音解码器、私有系统拼音调用或把通用 LLM 当作逐键中文候选生成器。理由是缺乏本项目可复现的质量、许可或延迟依据，并非认定这些技术永远不可用。闭源系统输入法可在合法公开行为范围内作为人工体验基线，但不是可复制进产品的解码器。

[中文专项](research-ime-engines.md#首轮实测组合与退出条件)把主赛细分为：青简静态/统计与知意重排开关、Rime 官方小鹤机制基线与雾凇/万象生产组合、libime Xiaohe 配出厂词典/语言模型。神经生成另列探索，不与统计模型混称“AI增强”；已查 Rime 神经插件仍有 Intel 产物、小鹤条件输入或独立权重许可缺口，暂不作为默认方案。

两条赛道分别报告：生产包赛道看用户实际体验；受控数据赛道尽量统一合法词表、目标与候选数，并披露无法统一的语言模型。不能把现代数据配一方、最简旧词表配另一方后，将差异全部归因于引擎。

调参与最终验收使用分开的输入集。已有 32 条翻译合成样例适合回归已知风险，不足以代表真实用户质量。补充由实际交流任务改写且不含个人信息的保留集；中文目标允许多个合理候选，译文由懂两种语言的人在隐藏后端名称的条件下逐条审阅。数字、否定、人物和方向错误单列，避免被大量简单正确句平均掉。自动指标可辅助定位变化，不能替代含义与可用性审阅。

## 学习模式还有一个必须解决的交互问题

输入中文、选择中文词、选择英语义项是三个可能不同的动作。默认仍遵守“选词后直接上屏英语、不额外打开编辑器和确认翻译”。因此应把中文来源和英语表达的关系放进同一候选体验，而不是默认让用户先选中文、再过第二次确认。

一个中文候选可能对应多个英语表达；一个双拼串也可能对应多个中文候选。若把二者简单做笛卡尔积，会增加翻页并削弱候选质量。建议实验“英语表达加简短中文含义”的统一候选项，保留明确的来源区间和候选身份；选中该项只提交它所显示的目标表达。具体排版和按键需原生验证，当前浏览器原型不能代替此结论。

神经模型在等待时，不能把“加载中”占成可提交结果，也不能让默认空格悄悄提交中文。结果在用户按确认的同一时刻到达时，也不能把原先高亮项替换成另一项而造成误选。可考虑候选批次固定或保留稳定高亮身份，待交互验证。

词级逐段提交也有句级限制。例如“我想/开会/明天”逐段翻译后，通常无法靠候选缓存自动得到自然的整句；已经提交的文字不能静默重写。首阶段仍需要独立的整句入口，但不能强制所有词级输入等待整句。该入口、英语空格是否只是词边界、Enter/标点怎样确认句子，仍是待验证设计。

已有模型对 `metting` 的输出不稳定。拼写标记、翻译内容与自动采用资格必须分别处理；不能用非空输出、beam score、往返翻译或没有红线，自动证明译文可靠。词典与短语资源也有覆盖与义项选择风险，不构成任意自由句都安全的保证。

[资源核查](research-ime-learning.md#资源许可与覆盖核查)给出可继续评估的具体来源：CC-CEDICT 可供中文词头与英语释义检索，Tatoeba 可筛选直接中英句对并人工审阅；前者的 CC BY-SA 与后者逐句许可、作者归属分别保留。ECDICT 虽有仓库 MIT 声明，汇编数据的具体来源仍需补核。三者均不是已经可直接装入输入法的合格表达包，不能把词条英语释义整段发送，也不能简单倒排实现另一个方向。

## 并发和资源：只快一个请求不够

建议开始采用“一项执行中，加一项最新待执行任务”的有界调度，再根据观测调整。无效的旧输入可以淘汰，用户已确认的提交意图需要单独保存状态，不能当作随手可丢的预计算。过期回调丢弃、取消尚未开始任务、实际中止正在执行的推理是三种不同能力。

每个结果至少绑定会话/宿主代次、输入版本、模式方向和资源版本。文本相同不能证明同一上下文：退格重输、换输入框、词库/模型更新与方向切换后都可能不同。提交前重新校验当前会话；提交只由输入控制器发起，工作进程不能自行向曾经的宿主写字。宿主焦点身份仍需结合实际事件验证，不能假定每次换字段都会收到一对完整 activate/deactivate 回调。

[学习专项](research-ime-learning.md)核对 CT2 v4.6.0：`asynchronous=True` 并不免除队列满时的提交阻塞，逐 token 停止回调只支持 greedy 的 `beam_size=1`，也不能即时打断 encoder/算子。工作进程自身须非阻塞接收输入版本，并在调用后端前控制排队；前端仅丢弃回调不能阻止旧计算继续占 CPU。宿主插入没有跨进程的事务去重协议，插入结果不明时不能自动重试并宣称端到端 exactly-once。

预计算应等到有意义的词/短语边界或短暂停顿，不把每个未成形的双拼字符都送进模型。缓存必须按方向、上下文、模型/词典版本区分；初期优先小型内存缓存，避免默认把输入历史持久化。具体防抖时长、预取数量、空闲释放策略通过真实输入比较决定。

CT2 官方提示线程总量 `inter_threads × intra_threads` 不应超过物理核数，并说明 batch/beam 等影响性能。[P4] 这也不是允许输入法占满所有物理核的建议；应给 UI、宿主和其他应用留预算。ORT 文档明确线程池 spinning 会用更多 CPU 和电量换取部分延迟收益，默认线程配置也可能随多个 session 放大资源竞争。[P5]

因此比较应同时记录普通输入在模型并发下的 p95/p99、模型等待与实际执行时间、废弃任务耗时、空闲 CPU 和长期热状态。不能仅因模型跑得更快就给它更多线程；不能仅因进程 RSS 降低就认为总系统占用更低。当前目标机有 64 GiB 内存，也要测试内存压力、两个方向轮换、长时间输入后缓存增长及空闲恢复，不能只测刚启动时的峰值。CPU、MPS、Core ML、ORT 等仍是待测后端，已有 MPS 回退的差成绩不排除所有 GPU 实现。

Apple 的节能指南建议用适当 QoS 区分用户交互和维护工作，并减少无效定时唤醒。[P7][P8] 不为了 benchmark 常年禁用 App Nap；用户正在等结果的工作与词库索引、记录整理采用不同优先级。系统是否调度及时仍以目标机实测为准。

## 下一轮的建议验收与计量

以下数值是用于暴露问题的初始工程目标，**尚未由用户确认，也不是已达标能力或行业统一标准**。先记录现有可用输入法的体验基线，再据真实宿主、刷新率和输入长度校准。

| 路径 | 建议初始目标 | 报告必须附带的条件 |
| --- | --- | --- |
| 每键主线程处理与 UI 准备 | p95 尽量 ≤5 ms；单独追踪超过一帧与 50 ms 的事件 | 只计输入法主线程工作，不当作屏幕可见延迟 |
| 热态普通输入按键→候选可见 | p95 ≤30 ms、p99 ≤50 ms | 按短词/长句/局部编辑分桶，注明录屏/显示采样误差 |
| 已准备候选的确认→宿主显示 | p95 ≤30 ms | 不含等待尚未生成译文；每种宿主分别报告 |
| 词典/表达缓存命中→候选可用 | p95 ≤30 ms | 不混入神经模型、磁盘冷读或输入法显示耗时 |
| 神经模型学习候选 | 先测完整分布，短表达争取 p95 ≤200 ms | 属于探索目标；现有混合中位数不能证明，长句另列 |
| 冷启动、资源恢复与服务重启 | 单独记录，期间普通输入仍能工作 | 首次安装、文件缓存、已加载/卸载、方向切换分别测 |
| 正确性与安全性 | 定义的竞态/失败场景里无丢字、重复或串宿主提交 | 同时保存事件序列；有限测试通过不证明所有场景零缺陷 |

推荐测试分三组，避免未经确认的一组权重把质量问题平均掉。

1. **中文质量与逐键性能**：覆盖日常聊天、工作表达、新词姓名、双拼歧义、长句、局部改写、代码混输；每个目标允许合理备选。报告首选命中、Top-k、目标完成按键数、候选排序变化与返工次数。学习关闭和固定学习轨迹分开。
2. **学习输入质量与负载竞争**：双向逐条审阅词义、上下文、数字/时间/否定、错拼、名称和简繁；并行重放普通输入，报告其是否退化。检查不同精度、模型、词典覆盖和 fallback；失败数不能从延迟统计中消失。
3. **真实宿主与失败恢复**：输入框和窗口切换、模式切换、鼠标点说明、Esc/Enter/空格、睡眠唤醒、缺模型/进程终止/磁盘满/更新中断、长按连发、非美式布局、全屏多屏。宿主矩阵详见 macOS 专项。

固定 Release 构建、架构、引擎与资源哈希、候选上限、线程/模型参数；交错顺序，多轮运行。逐键正式测量建议至少约一万次事件并按场景披露样本数；p99 尾部仍需看原始慢样例，不能用十条句子的平均值证明顺畅。记录后台负载、插电状态、热状态、文件缓存与测试工具开销，不擅自结束用户程序。

用 signpost 按请求/输入版本串起事件、解码、候选构建、任务排队、翻译和提交时间线，只记录随机 ID、长度、状态和时长。[P2] 不记录原文、可逆缓存键或把输入文本放入 signpost 名称。正式计时与 profiler 采样分开，避免用高频即时 trace 的额外开销给方案排名。

## 下一步工作的顺序

1. **扩展固定输入与安全约束**：已冻结 40 条中文探索样例及基础操作轨迹；继续补两向学习候选、真实任务按键、修订及失败事件，另建独立质量保留集。用合成文本，不读取个人历史。
2. **扩展中文赛道实测**：青简统计配置、Rime 官方／雾凇／万象小鹤与 libime 出厂数据已完成首轮核心对照；两轮均有 CPU 速度限制，不能称正常频率排名。优先将 libime 与雾凇接入相同原生前端，同时按相同门槛补入 libpinyin、SunPinyin 等解码库。以实际输入速度、候选质量和长尾延迟优先，再综合内存、耗电与维护成本；不同数据的核心耗时不能单独决定产品底座。
3. **做可抛弃的原生最小闭环**：同一套轻量 UI/宿主适配接候选引擎，先使用固定译文隔离输入协议，再接有界真实翻译服务，观察负载竞争及焦点安全。这是下一轮建议，本轮尚未开始实现。
4. **补齐学习资源与译文质量**：词典义项、常用表达和其他可分发模型分别验证；若自由句质量仍不合格，明确保留未完成状态，不能把词级成功冒充首阶段全部达标。
5. **再确定技术组合与分发方案**：依据真实输入、许可与兼容性选定前端/引擎/数据/翻译后端，再实现满足使用需求的后台管理。没有理由先做高规格后台来决定核心结构。
