# 中文输入引擎首轮实测

实验日期：2026-10-30。依据[产品方向](product.md)和提前冻结的[实验方案](input-engine-benchmark-plan.md)，在当前 Intel Mac 实际装配并比较五套小鹤配置。本文报告中文核心查询与提交探针，不代表 Gogaku 原生输入法、屏幕响应或翻译并发已经实现。

**本页保留首轮阶段判断；后续已补独立质量集及受控AppKit测试，首阶段采用libime出厂组合＋原生前端，见[技术选型决定](input-selection-decision.md)。** 以下首轮的测试边界和原始成绩不变，不把后续工程选择解释成全球性能排名。 两者在本组样例中兼顾了候选与延迟，但各有取舍。候选范围继续开放，libpinyin、SunPinyin、Google 开放拼音及不同前端的核查见[其他路线](research-ime-alternatives.md)。

## 测了什么，环境有什么限制

- MacBookPro16,1，Intel x86_64，8 个物理核／16 个逻辑核，64 GiB 内存；macOS 26.7.2，build 25G332，接交流电。Python 3.15.2，Rust/Cargo 1.99.1。每阶段保存实际环境和依赖记录。
- 40 条合成目标、每轮 320 次按键，覆盖日常、工作、学习、技术词、实体、多音字、歧义与零声母；最长目标 14 个汉字。不是实际用户输入分布，也没有独立质量保留集。
- 每次完整实验各配置运行 33 轮，每配置 10,560 次按键；两次共 **105,600 次正式按键事件**。所有输入前 reset，关闭用户学习、云能力、神经重排及翻译。五进程驻留，轮次按配置交错顺序运行。
- 性能与质量使用不同进程。性能连续满速串行回放、没有人工打字间隔，也不提交候选；先全样例预热。质量额外选择目标，检查 commit 与 composing。两轮的前十候选顺序和质量计数完全一致，但仍然只有 **40 条不同质量样例**。
- 所有构建、数据转换与词库部署结束后才开始正式计时；没有停止用户程序、清系统文件缓存或改变节能配置。

**两次都受到 CPU 速度限制，均不能叫正常频率或无背景干扰的基准。** A 轮计时开始／结束后的 `CPU_Speed_Limit` 为 43／60；A 后空闲检查曾恢复到 100，再次运行进入连续负载后，B 轮计时开始／结束后为 35／37。因此完整保留 A、B，不挑一个更快的结果发布。这个字段是系统报告的速度限制，不是本实验测得的实际时钟，也不能单独确定限速原因。

A 的计时窗口为 14:49:27–14:53:35，B 为 14:58:37–15:05:27。各轮负载、进程累计 CPU、RSS 与全部原始事件均保存。这些数据能暴露当前条件下的配置差异，不能证明普遍性能排名或真实打字延迟达标。

本组样例中，现代 Rime 配置比官方机制基线覆盖更多目标；不能由 R0 的成绩外推 librime 的质量上限。39 与 38 仅差一道题，不足以推断一般质量优势。

主要偏差如下，完整候选、每一步与实际选择结果见 [A 轮质量输出](../probes/results/input-engine-benchmark/quality-outputs.md)，[B 轮质量输出](../probes/results/input-engine-benchmark-repeat/quality-outputs.md)一致。

- 雾凇和万象都将「我们下周再讨论」首选为「我们下周在讨论」，目标不在前十。保留错误，未根据结果增加目标别名。
- libime 的「小鹤双拼」首选为「小和双拼」，前十有局部候选「小鹤」，但没有完整目标。用户仍可分段选择，不能把这条记成完全无法输入；本轮没有测其实际额外按键数。
- 青简的较长目标「我想每天花一点时间学习英语」得到「我想每天画一点时间学习英语」；「小鹤双拼」也未一次命中完整目标。「飞书」位于第三项，实际选择后完整提交。
- 官方 Rime 基线还出现「请再说一边」「开会的事件」等同音偏差；雾凇和万象在本组对应样例命中了预设目标。

候选精确出现与一次完成分别评分。匹配项若只消费前缀、留下 composition，不能算整段完成；这不取代后续局部选词、翻页和实际任务按键评估。

## 逐键核心墙钟时间

计时覆盖按键处理／查询更新、**真实生成并复制前十候选**、预编辑和提交状态提取，止于 JSON 编码之前；不含 stdin 等待、JSON 解析／编码、父子进程通信、UI 或宿主显示。适配器的状态复制与临时对象构造仍存在差异，因此也不是纯算法内核排名。

单位为 ms，所有配置每轮次实验均为 n=10,560。两轮完整列出，p99 表示约 99% 的本轮样本不超过该值，不是最慢值。

| 配置 | A p50 | A p95 | A p99 | A 最大 | B p50 | B p95 | B p99 | B 最大 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Q0 青简统计配置 | 1.01 | 7.31 | 14.34 | 66.90 | 1.75 | 12.31 | 24.58 | 60.65 |
| R0 官方 Rime | 0.53 | 1.43 | 1.96 | 42.60 | 1.01 | 2.60 | 5.96 | 29.56 |
| R1 雾凇小鹤 | 2.34 | 6.03 | 8.75 | 80.95 | 4.44 | 13.85 | 17.96 | 79.31 |
| R2 万象标准版小鹤 | 8.06 | 25.06 | 43.58 | 115.20 | 14.95 | 39.90 | 53.30 | 172.92 |
| I0 libime 出厂组合 | 1.69 | 5.84 | 9.66 | 94.57 | 2.93 | 10.98 | 17.88 | 89.03 |

libime 的中位数低于雾凇，二者 p99 在 B 轮相近；青简的中位数更低，但本组长尾与内存成本较高。万象在本组未增加首选命中数，却有更高逐键成本；需要较大质量集与 grammar／Lua 消融查清收益，不能只凭这 40 题淘汰其全部配置。

较低中位数不能掩盖最大值。这里是墙钟时间，区间内的系统抢占也会计入；没有逐事件 CPU profiler，不能把所有慢样本都认定为算法计算。分场景、最终一键、process／collect 和父进程往返分布均在两轮 `measure/measurement-summary.json`；原始按键与慢样本可从 `events.jsonl.gz` 复查。

RSS 来自每轮结束的 `ps` 采样，**不是真实瞬时峰值，也不是总系统物理占用**；共享映射与内存压缩等尚未分析。CPU 增量包含该进程的 reset、查询和协议处理等工作，不是纯解码 CPU。未测空闲唤醒、能耗或长时间缓存增长。

A 轮计时进程从启动到 ready 的单次观测依次为：Q0 861 ms、R0 51 ms、R1 153 ms、R2 3,694 ms、I0 155 ms。文件缓存没有清空，且每进程新建隔离用户目录，部分 Lua 缓存需重新生成；这些不能叫磁盘冷启动分布，也不能直接代表日常保留缓存后的产品启动时间。各阶段逐个样本、worker 内部 load_ms 及其不同边界保存在 startup.json；部署／编译时间没有计入按键时间。

## 提交、隔离与装配检查

- 五套配置均通过 reset、逐键、peek、非首候选选择、部分选择、退格、取消和重复输入的冒烟轨迹；质量 pass 实际选择匹配项，没有把非空输出当作正确。
- Rime 质量样例用新 session 清除 commit_history；只 clear_composition 不足以保证独立上下文。性能 pass 不提交，关闭用户词典及相关 Lua 学习路径。
- 两轮均以 sandbox-exec 禁止 worker 网络，加载本地材料后完成代表轨迹。另用 socket 连接建立拒网对照，确认为 Operation not permitted；没有由此声称全机或未来进程外服务已经断网验收。
- 两轮全事件覆盖校验通过：每配置、每轮、每样例按键次序完整，编码缓冲匹配前缀，没有未处理键或意外 commit，时长覆盖 process＋collect。正式阶段日志未发现 Lua 初始化错误或 panic。
- 实验后按准备时哈希复核 336 项 worker、实际加载数据及 Rime 运行资源，零不匹配，见[完整性记录](../probes/results/input-engine-benchmark/source-integrity.json)。原始 manifest 保留材料来源与许可记录。
- 装置另用合成 worker 检查：正常全流程通过；前十含目标但只提交前缀时完整提交得分为零；删除一个正式事件后汇总拒绝通过，并移除旧的成功汇总。

装配期间曾遇到 Fcitx5Utils 的 Apple libc++ `osyncstream` 编译缺项，隔离构建加 `-fexperimental-library` 后通过；Rime 现代 Lua 从 user_data_dir 查公共资源导致初始化失败，补齐资源映射并隔离可写 build 数据库后通过。早期失败日志保存在 A 的 `preparation/`，不计成引擎质量失败。没有为通过测试而将雾凇／万象替换成官方最简方案。

所有外部源码、数据与构建产物留在 `/tmp/gogaku-ime-benchmark/`；仓库保存自编探针、合成样例与结果。未读取个人词库／输入日志，也未安装、注册或切换系统输入源。

## 复跑

当前脚本固定本机 Intel macOS 与公共鼠须管路径。需要 Python、Rust/Cargo、Clang、CMake/Ninja 和准备脚本检查的现有 Homebrew 依赖；脚本不自动注册输入源。`qingjian-input-worker/Cargo.toml` 是由准备脚本在临时目录渲染的模板，不能直接在仓库内 cargo build。

```bash
python3 probes/prepare-qingjian-input.py
python3 probes/prepare-rime-input.py
python3 probes/prepare-libime-input.py
```

等待全部构建与部署结束，检查 manifest 的可用配置、实际 CPU 限制与背景负载，再运行到一个全新输出目录：

```bash
python3 probes/benchmark-input-engines.py \
  --manifest /tmp/gogaku-ime-benchmark/qingjian/manifest.json \
  --manifest /tmp/gogaku-ime-benchmark/rime/manifest.json \
  --manifest /tmp/gogaku-ime-benchmark/libime/manifest.json \
  --rounds 33 \
  --output-dir /tmp/gogaku-input-engine-rerun
python3 probes/summarize-input-engine-benchmark.py /tmp/gogaku-input-engine-rerun
```

准备 manifest 描述「装配／冒烟完成，未做正式性能」的时点；正式状态以各阶段 status.json、原始事件及最终 summary.json 为准。汇总会核对样例、配置、runner 哈希与事件覆盖，拒绝覆盖既有测量阶段。

A 的[汇总](../probes/results/input-engine-benchmark/summary.json)和 B 的[汇总](../probes/results/input-engine-benchmark-repeat/summary.json)均保留原始数据、输入快照、环境、日志和 artifact-hashes.json。

## 后续顺序

1. 优先把 libime 出厂组合与雾凇小鹤接入同一可抛弃原生前端，验证人工打字节奏下按键到候选可见、确认到宿主实际收字、局部选择及焦点安全；不将上表直接当作 UI 成绩。
2. 核对具体模型数据授权后加入 libpinyin、SunPinyin；继续对照自建 AppKit、OpenVanilla 和 Fcitx 集成路线，不锁定在现有三家核心。
3. 加入较大独立质量保留集、实际任务按键、受控词表、参数消融和用户学习轨迹。当前 40 题没有覆盖任意长度、任意修订、标点代码混输或所有新词。
4. 在相同输入链路加入有界真实翻译服务，记录输入 p95/p99、排队、过期计算、CPU 与内存。中文核心快不代表双向学习输入已顺畅，更不证明现有翻译质量已经合格。
